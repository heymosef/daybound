Status: investigation complete; implementation has not started. This is an audit and sequencing report, not a set of executor implementation plans.

## Scope and verified baseline

- React 18 / Vite 6 static application deployed through GitHub Pages; state lives in localStorage. No application backend, authentication, or database was found.
- The checkout was clean before this report. Last local commit: March 3, 2026. GitHub searches returned no open PRs or issues. The remaining `date-picker` branch is already merged into `main`; there are no local stashes. This branch is cleanup, not unfinished feature work.
- `npm test -- --reporter=verbose`: **27 passed, 2 failed**, across two test files. Both failures are ambiguous month-text queries in DatePicker tests, not evidence that those two date computations are wrong.
- Production Vite build succeeded with `build.write=false`, without replacing existing dist output. JavaScript: **592,949 bytes / 188,408 bytes gzip**. CSS: **48,296 bytes / 9,841 bytes gzip**. This is a build check, not a deployed-browser test or TypeScript check.
- `npm audit --json`: **26 affected packages: 3 critical, 8 high, 14 moderate, 1 low**. These are package counts, not counts of exploitable application vulnerabilities. Advisory conditions were reviewed for the principal high/critical paths.
- Direct Node probes reproduced fractional-zone day anchoring and midnight selection drift. An in-memory React render using the existing persistence hook reproduced null-settings and blocked-storage failures.
- Reviewed application components, persistence/time hooks, timezone helpers, styles, dependencies, build/deployment configuration, tests, local Git history, and repository backlog. Narrow read-only passes covered correctness, performance, and security; the primary reviewer checked the retained code evidence.
- Not audited: live production traffic or headers, actual PostHog project/remote settings, GitHub environment secrets/protection rules, mobile/browser behavior, full accessibility, comprehensive historical secret scanning, or a dynamic penetration test. No installs, source fixes, commits, pushes, or deployment changes were made.

### 1. Verification baseline and CI

Evidence: `src/app/components/DatePicker.test.tsx:317–319,398–401` scopes assertions to the Back to today button's parent, which also contains multiple month labels. `package.json:6–10` exposes only dev/build/test/watch scripts; there is no tsconfig or lint configuration in the tracked inventory. `.github/workflows/pages.yml:3–6,32–44` runs on main pushes/manual dispatch and goes from installation to build to artifact upload without tests.

Repair the two assertions by querying the specific button. Add explicit TypeScript configuration, required types and `typecheck` script, and a lint baseline. Add PR validation; make deployment depend on validation. Introduce targeted tests with the fixes below, especially Timeline and persistence, which currently have no dedicated tests. Do not assume Vite's successful TSX transpilation means the project passes TypeScript checking.

### 2. Dependency and runtime maintenance

Evidence: `package.json:34–39` pins Vite 6.3.5 and retains a pnpm-only Vite override, while deployment uses npm ci. `package-lock.json:3945,4020,3582,3776,3485` records Vite 6.3.5, Vitest 4.0.18, Rollup 4.58.0, tar 7.5.9, and protobufjs 7.5.4 respectively. `.github/workflows/pages.yml:29` selects Node 20, which is now EOL. See [Node release lifecycle](https://nodejs.org/en/about/eol).

Patch the graph with npm, with one owner for package.json/package-lock.json. Audit currently suggests Vite 6.4.5 within its major and Vitest 4.1.12 within its allowed range; recheck advisories at implementation time. Refresh affected transitives and PostHog together, remove or reconcile the ineffective pnpm override, and move CI to a supported LTS such as Node 24. Review GitHub Actions versions and minimize job permissions as part of the same deployment review. Establish automated dependency update PRs so maintenance does not depend on the next manual audit.

Actual exposure distinctions:

- **Vite:** the [file-read advisory](https://github.com/advisories/GHSA-p9ff-h696-f583) applies when the development server is exposed to the network. The checked-in command/config does not enable that exposure. It does not apply to static GitHub Pages serving dist files. Patch before network-exposed development.
- **Vitest:** the [critical advisory](https://github.com/advisories/GHSA-5xrq-8626-4rwp) concerns exposed UI/API capabilities. Checked-in configuration uses jsdom and the test script is `vitest run`; no UI/API exposure is configured. Upgrade, but do not describe this as demonstrated public-site RCE.
- **Rollup/PostCSS/tar and other transitives:** these belong to the active build/install graph. [Rollup's advisory](https://github.com/advisories/GHSA-mw96-cpmx-2vgc) requires attacker influence over output names/plugins; source-map/archive advisories likewise have input preconditions. Patch this distribution path, while distinguishing it from a public request endpoint. Exploitability of every transitive advisory was not individually established.
- **protobufjs:** arrives through PostHog's OpenTelemetry dependency. The [critical schema-code-generation advisory](https://github.com/advisories/GHSA-xq3m-2v4x-88gg) requires untrusted protobuf schema/descriptor input, which application code does not accept. Installed generated OTLP code uses `protobufjs/minimal`; the browser logs exporter uses JSON serialization. The freshly built main chunk's module list contains no protobufjs. Refresh the graph; no reachable application RCE was established.

Avoid a blanket major-version migration or `npm audit fix --force` as the first step. React 19 / Vite 8 / newer Motion migrations can be evaluated later, separately from the bounded patch pass. [Vite's release policy](https://vite.dev/releases) currently lists security backports to Vite 6.4.

### 3. Calendar resets on every tick

Evidence: `src/app/components/CalendarDropdown.tsx:61–65` resets viewingMonth when now changes. `src/hooks/useTime.ts:7–9` supplies a fresh Date every second. A user navigating to the next month loses that navigation at the next tick. Existing tests use fixed now values and miss this interaction.

Initialize the month on opening, ideally from the selected date, and explicitly handle home-zone/day changes without resetting ordinary navigation. Add a test that navigates, advances now, and verifies the viewed month remains stable. Confidence: high from the deterministic effect/prop chain; no interactive browser reproduction was performed.

### 4. Fractional timezone offsets

Evidence: `src/app/App.tsx:277–283` computes home midnight correctly, then `src/app/components/Timeline.tsx:104` rounds that instant using browser-local startOfHour. `Timeline.tsx:419–421` hides minutes; `:358` treats any time with hour zero as midnight.

Reproduction: browser zone America/Vancouver; home Asia/Kathmandu; now 2026-10-22T18:00:00Z; selected offset 1. Intended home day begins **2026-10-23 00:00**; the current first timeline cell begins **2026-10-22 23:45**. Rounding and integer-only labels also misrepresent comparisons involving half-hour offsets.

Preserve the supplied day-view instant, define a shared instant-based rail, display minutes where needed, and place true date boundaries correctly. Test UTC, Kathmandu, Kolkata, Adelaide, different browser/home zones, and DST transitions. Keep cross-row hover alignment and live-marker behavior intact. This is the highest-risk correctness change because several visual calculations share the anchor.

### 5. Persistence recovery

Evidence: `src/hooks/useStorage.ts:11–15` checks only typeof and array-ness; null passes the object check for settings, and malformed array entries/invalid timezone identifiers pass too. `:19–21` catches a failed read, then calls removeItem without guarding a second storage failure. `src/app/App.tsx:159` immediately reads settings.designTheme, while `TimezoneRow.tsx:75–78` formats timezone data.

The existing hook reproduced a TypeError for persisted null settings, and a SecurityError when both storage read/removal are blocked. This is a resilience problem; no external attacker-controlled write path was established. Validate each stored schema and IANA identifier, merge valid old settings with defaults, guard every storage operation, and retain usable in-memory state if persistence fails. Make the local-save promise at `App.tsx:463` reflect actual save availability.

### 6. Analytics data minimization

Evidence: `src/app/App.tsx:180–186,384–385` sends a home city's arbitrary editable label as home_city. `src/app/components/AddTimezone.tsx:31–41,238–245` sends sanitized failed-search phrases; stripping punctuation/digits does not anonymize people's names or confidential words. `src/main.tsx:7–10` opts out only for hostname localhost and relies on SDK defaults otherwise.

Use canonical timezone identifiers instead of editable labels, replace free-text failed searches with counts/coarse categories, and explicitly configure autocapture/text masking and the intended opt-out behavior. Include loopback development variants. Test payload contents with a mocked/offline client so verification itself does not send analytics. Review actual remote replay/log settings separately; they were not available in this source audit. This is a confirmed code-level privacy concern, not a legal compliance determination.

### 7. Selected date silently drifts

Evidence: `src/app/App.tsx:264–265,279–283` stores a relative offset and recomputes it against changing home today. `DatePicker.tsx:29–30` uses the same moving reference. Home changes at `App.tsx:372–385` do not reconcile selection.

In a Kathmandu probe with offset 2, advancing now from 2026-10-22T18:00Z to 19:00Z changed the selected date from October 24 to October 25. Decide whether choosing a calendar date means a fixed date or a rolling N days ahead. For a fixed date, separate live mode from the selected calendar date and define behavior on home-zone changes. Confidence: high for the behavior, medium that it violates intended product semantics; resolve that decision before implementation.

### 8. Performance opportunities

Evidence: `src/hooks/useTime.ts:7–9` updates every second although `Timeline.tsx:101,134–137` and `TimezoneRow.tsx:216–220` show minute precision. `Timeline.tsx:108–118,148–159,350–355` rebuilds 25 cells and converts timezones in two passes on every render. Fresh Date and callback props prevent the existing React.memo boundaries from skipping this work. `App.tsx:429–431` also constructs a fresh search-input array, invalidating `AddTimezone.tsx:64–124` memoization on ticks/hover.

Use an aligned minute clock with an immediate visibility/focus refresh; memoize stable rail data by timestamp/zone/format and stabilize search inputs. Profile representative timezone counts first, then optimize demonstrated hotspots. CPU/battery savings have not been measured.

The main bundle is 188 KB gzip. A separate in-memory module-attribution pass found Motion and PostHog among the largest contributors before minification; these attribution sizes are not compressed transfer sizes. Evaluate lazy animation features or analytics loading after correctness work; do not assume unused culori is in the browser bundle. `src/styles/fonts.css:1–3` makes three external font stylesheet requests; consolidate or self-host if a cold-cache waterfall shows benefit. Font binaries generally load when their family is used, so three stylesheets do not establish three font-family downloads on every visit.

### 9. Stale work and onboarding

Evidence: unused culori at `package.json:15`; unused formatTimezoneTime helper/imports at `src/utils/timezoneUtils.ts:1–2,57–72`; tracked `.cursor/debug-99805d.log:1` contains old local diagnostic metadata; `guidelines/Guidelines.md:1` remains scaffold; README development instructions omit npm ci, dev/test commands, and PostHog variable setup. No `.env.example` is tracked.

Remove obsolete diagnostics and ignore future logs, remove verified-unused dependencies/helpers, document supported Node/npm and verification commands, provide a placeholder-only env example, and document operation when analytics configuration is absent. The merged date-picker branch can be removed when convenient. No private credential signature was detected in the bounded history review; this is not a guarantee that every historical secret was excluded. No `.env` file is tracked. Public PostHog ingestion keys are expected in client builds and are not equivalent to private API credentials.

## Work ordering and parallel ownership

1. **Establish the release baseline.** Fix the two test selectors first. Keep package/runtime/dependency/CI edits with one toolchain owner; add typecheck/lint and PR/deploy validation, then patch and revalidate. Persistence regression-test design and privacy payload inventory can proceed independently while the toolchain work runs. Do not wait for a framework rewrite to patch advisories.
2. **Repair correctness, persistence, and privacy in parallel.** A date owner handles calendar navigation, timeline anchoring, timezone matrix tests and selected-date semantics. A persistence owner handles useStorage and focused hook tests. An analytics owner handles capture configuration/payloads. Calendar regressions and baseline selector changes share DatePicker.test.tsx, so begin calendar edits after the baseline lands. Date and analytics work both touch App.tsx: preassign nonoverlapping sections or stage App integration through one owner rather than concurrently rewriting it.
3. **Optimize after date behavior is stable.** One render-performance owner handles the clock, date-derived computations, search props, and memoization together. These overlap the date fixes and depend on their regression cases; do not run them concurrently with timeline/date-state rewrites. Fonts, onboarding docs, and diagnostic cleanup can proceed independently with dedicated file ownership.
4. **Integrate and validate the final candidate once.** Each stream owns its focused tests. On the combined candidate, one owner runs clean install, the complete test/typecheck/lint/build gates, and a fresh dependency audit; then checks the actual browser flows for live ticking, future-month browsing, fractional offsets, DST, midnight rollover, storage recovery, and offline analytics payloads. Scope subsequent reruns to new changes or failures. Compatible reviewed changes may share one PR/release; separate review boundaries do not require separate releases.

Shared-file rules: one package.json/package-lock.json owner; one date/clock owner at a time; explicit App.tsx integration ownership. This is enough parallelism for this small codebase without multiplying conflicting branches.

## Grounded optional product directions

- **Portable dashboard configuration:** localStorage is the sole persistence mechanism and the UI explicitly promises local saving (`App.tsx:463`). A validated export/import feature would let users back up or move a setup without introducing accounts. Coarse effort M; it expands the untrusted-input boundary, so finish schema validation first.
- **Explicit working-hour overlap:** Timeline currently hardcodes daytime to 07:00–19:00 (`Timeline.tsx:357`) while the README positions the product around distributed-team working hours. Per-zone working hours and an overlap view could make this promise more useful. Coarse effort L; requires product decisions and additional persistent schema, so defer until date correctness and migration behavior are reliable.

These are options, not defects or prerequisites for maintenance.
